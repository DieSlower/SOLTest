# SDD 33: Player documentation (key caps, keyboard diagram, HUD glossary, player guide)

Issue #33 ("Player documentation: all controls with keyboard pictures and a glossary of every GUI element"). Depends
on SDD 8 (menus, Controls / Info / About, key rebinding), SDD 21 (the hologram HUD renderer), SDD 22 (overlay icons,
interaction menus), SDD 42 (hologram menus and cards) and SDD 46 (the solid menu kit, the page shell, the tab pages,
the profile smoke and the VR floor). Plan: [`Docs/Plans/33-player-documentation-plan.md`](../Plans/33-player-documentation-plan.md).

Status: **Drafted 2026-11-06 from the resolved grill-me decisions (user, 2026-11-06), checked against the code at HEAD
`f397b00`.** Items marked **(proposed)** are starting values or design details that no decision fixes; they wait for
the user's approval (open question O11). **Section 18 lists the decisions still open; parts are gated on them as the
plan says. Nothing in this document decides them.**

## 1. Goal

A player can learn every control and every symbol on screen without leaving the game: a new **Help** page (main and
pause menus) shows a **keyboard and mouse diagram** of the live bindings, tinted by area, and a **HUD glossary** that
draws the real HUD symbols with the HUD's own shape code next to a plain explanation. Keys look the same everywhere in
the menus: the Controls page rows show **drawn key caps** instead of plain key text. A **game flag** renders the same
content into a generated `Docs/PLAYER_GUIDE.md` with screenshots, linked from the README, and a check flags a guide that
no longer matches the game. Everything is generated from the tables the game already uses (`SOLMenuText`,
`SOLKeyBindings`, `SOLConstants.h`), so the documentation cannot drift from the game.

## 4. Architecture

### 4.1 Overview

```
SOLMenuText (CONTROL_ROWS, KEY_SHORT_LABELS, GLOSSARY_ENTRIES)   SOLKeyBindings (live keys)   SOLConstants (numbers)
        |                                   |                                  |
        v                                   v                                  v
  pure: SOLKeyCaps (parse a bindings cell into caps)     SOLKeyboardLayout (key positions, hit test)
        SOLKeyDiagram (key -> area, labels, actions)     SOLGlossary (entries, tokens, coverage)
        SOLHudSymbols (symbol -> shape primitives)        SOLPlayerGuide (markdown)
        |                                                     |
        +--> SSOLKeyCapRow / USOLKeyCapRow  (Controls rows, Help)          +--> -SOLWritePlayerGuide: Docs/PLAYER_GUIDE.md
        +--> SSOLKeyboardDiagram / USOLKeyboardDiagram (Help > Keyboard)          and Docs/Images/33-help-*.png
        +--> USOLHudSymbolView (glossary rows, one small SSOLHudShapeLayer each, retained batch, M_SOLHudShape MID)
        +--> ASOLFlightHud draws the same SOLHudSymbols in flight (no behaviour change)
  Help page = USOLReadOnlyPageWidget of kind ESOLReadOnlyPage::Help in the page shell (main menu and pause menu)
```

Everything lives in the feature folders of what it serves (STYLE_GUIDE section 14.2): the cap, diagram, glossary,
guide and Help page code in `Source/SOLTest/Menu/`, the symbol builder in `Source/SOLTest/UI/` next to the HUD shape
code, each type's `.h` and `.cpp` side by side.

## 5. The Help page

- **Where (D2, D10).** Main menu: a **Help** entry in the column opens the Help page in the page shell. Pause menu: a
  **Help** tab opens it in the shell right of the side panel, like Controls (SDD 46 Q4). Back and Esc close it as any
  page. No binding opens it. **The entry's position and the stack cap are open question O1** (proposed: right after
  Controls in both stacks: Play, Demo, Start, Controls, **Help**, Settings, About, Quit and Resume, Controls, **Help**,
  Info, Settings, Demo, About, Quit).
- **Kind.** A `USOLReadOnlyPageWidget` of kind `ESOLReadOnlyPage::Help`: the tab rail beside the content recess, one
  scroll per tab, opens on its first tab every time, re-click a no-op (SDD 46 section 6.5). Tabs (labels per O6):

  | Group (caption) | Tab | Content |
  |---|---|---|
  | KEYS | Keyboard | Area legend, the keyboard and mouse diagram, the detail strip, a line pointing to Controls for the full list |
  | HUD GLOSSARY | Flight HUD | Glossary rows (section 8.4) |
  | | Targets and radar | Glossary rows |
  | | Overlays and route | Glossary rows |
  | | Menus and map | Glossary rows |

- **Glossary rows.** A symbol recess (`GLOSSARY_SYMBOL_BOX` 96 units square, proposed) holding a `USOLHudSymbolView`,
  then the entry's name (heading colour, SemiBold) and its description (body colour, wrapping), like the Info rows.
  At 1000x800 the description wraps under a narrower column (the 46i `LeftColumnWidth` rule; the symbol box may drop to
  `GLOSSARY_SYMBOL_BOX_NARROW` 64, proposed).
- **Live keys.** Key names in the glossary text and the diagram come from `ResolveLiveKeys` (the ship's mapping in
  flight, the applied settings in the main menu), as Controls and Info do. They are refreshed when the page shows and,
  while it shows, on `USOLSettingsSubsystem::OnKeyBindingsChanged` (bound in `NativeConstruct`, unbound in
  `NativeDestruct`).

## 6. Key caps (D3, D9)

- **Look (proposed, from the solid kit).** A cap is one hull box in the **Small** button style (`SOLSolidStyle`,
  normal state, the shared MID: no new material, D12), `KEYCAP_HEIGHT` 30 units, `KEYCAP_CHAMFER` 3, the legend in
  Rajdhani SemiBold `KEYCAP_FONT_SIZE` 15 in the text colour (#DCE3E8), `KEYCAP_PADDING` 8 a side,
  `KEYCAP_MIN_WIDTH` 30. **Wide caps:** Space (`KEYCAP_SPACE_UNITS` 4 x a unit), Backspace, Tab, Enter, Shift, Ctrl,
  Alt, Caps (by the key's layout width, or 2 units for a cap in a row). **Mouse buttons** (LMB, RMB, MMB, wheel, Mouse
  move) draw a small mouse glyph (body outline, two buttons and a wheel slot as `MakeLines` and boxes) with the used
  part lit in cyan (#28D2F0), plus a legend for the wheel ("Wheel") and the move ("Move"). **Unbound:** a recess-style
  cap with "Unbound" in the dim text colour.
- **Chords and alternatives.** A chord draws its caps joined by a small "+"; alternatives are separated by " / " in
  the dim colour, the same order as `FormatBindings` today. `SOLKeyCaps::ParseCell` produces the model; text and caps
  come from the same parse, so `FormatBindings` stays the text form (used by the HUD hints and the guide).
- **Controls page.** Every key cell becomes a `USOLKeyCapRow` in the same `KEY_COLUMN_WIDTH` 230 column. A row wider
  than the column wraps onto a second line inside the cell (pure `SOLKeyCaps::LayoutRow`), so the action column keeps
  its width. `RefreshControlsPage` hands each row its parsed caps on show; the rows sweep of `-SOLSmokeSolidMenu`
  (46i) checks every cap row inside its cell at 1000x800 and 1280x720.
- **Settings > Key bindings** keeps its text key cells unless the user answers O5 otherwise (the rebind waiting text
  and the 46i narrow rows are the risk there).
- **Info prose and HUD hints** stay text (they are sentences and HUD lines; D9 names the Controls rows).

## 7. The keyboard diagram (D4, D13)

- **Layout (proposed, O4).** A ten-keyless US layout: the function row (Esc, F1-F12), the main block (number row to
  the Ctrl / Alt / Space row, with Left and Right Shift, Ctrl and Alt as separate keys), the navigation cluster (Insert,
  Home, Page Up, Delete, End, Page Down) and the arrows; no numpad. Positions in key units in `SOLKeyboardLayout`'s
  table (about 87 keys), with the mouse drawn to the right (LMB, RMB, wheel / MMB, the move arrows). The diagram scales
  to the content width (`KeyUnitPx` = width / `Extent().X`, clamped to `DIAGRAM_MIN_UNIT` 24 .. `DIAGRAM_MAX_UNIT` 46
  units, proposed); below the minimum the short labels hide and only legends and tints remain (hover still works).
  A binding on a key not in the layout (a numpad key, a media key) shows in an **"Other keys"** strip under the
  diagram as a cap with its tint and label, so no live binding is ever invisible.
- **Which keys (O4).** Every key named by a `CONTROL_ROWS` cell: the `@` bindings through the live keys **and** the
  fixed keys of the rows (map J / M / P, X, Enter, Delete, Esc, Ctrl+F1, Ctrl+F2, the mouse drags, the wheel), the
  fixed ones with a small lock mark (proposed) since they cannot be rebound.
- **Areas and tints.** Each assigned key is tinted by its area: a translucent area-colour fill over the cap face
  (`DIAGRAM_TINT_ALPHA` 0.28, proposed) and an area-colour bar along its lower edge, with the short label in the area
  colour. Area palette (proposed, picked to stay apart from the amber hover and readable on gunmetal): Flight #28D2F0
  (the kit cyan), Targeting #F2C94C, Combat #E5533D (the kit warning red-orange), Time #9B7BFF, Overlays #4CD07D, HUD
  #5B8CFF, Map #FF8FB1. **Routes, Menu and Demo are areas of the rows but not in D4's list: open question O2**
  (proposed: Routes shares Map's colour, Menu and Demo a neutral #A4AFB8 "System" tint).
- **Several actions on one key (O3).** A key with more than one assignment (O x4 with chords, M, X, P, J, LMB, RMB,
  Left Shift, the wheel) is tinted by its **primary** assignment: the plain (no chord) in-flight action, else the first
  row that names it (proposed). Its short label is that action's; a badge in the top-right corner shows the number of
  further actions ("+3") and a pip per chord modifier colour (proposed). Hover lists all of them.
- **Short labels.** A new table `SOLMenuText::KEY_SHORT_LABELS[]` (one per binding, `EBinding` order, `static_assert`
  on the count, at most `SHORT_LABEL_MAX_CHARS` 8 characters, proposed: "Fwd", "Back", "Left", "Right", "Up", "Down",
  "Roll L", "Roll R", "Boost", "Assist", "Stop", "Steer", "Steer on", "Look", "Center", "Speed", "Target", "Next",
  "Prev", "Clear", "Match", "Lock", "Fire", "Drop", "Warp -", "Warp +", "Warp 1x", "Overlay", "Orbits", "Ov menu",
  "Profile", "Radar -", "Radar +", "Radar A", "Map", "Jump map", "Resume", "Routes") and `FIXED_KEY_SHORT_LABELS` for
  the fixed rows' keys ("Jump", "Move", "Patrol", "Go", "Del rte", "Menu", "Stats", ...). Final wording is part of O11.
- **Hover (O7).** Hovering a key (the mouse; the Help page has no keyboard focus inside the diagram, SDD 46 D6) lifts
  it like a hovered button (the amber edge and lift, `HOVER_RAMP_S` 0.12 s, instant at strength 0) and fills the
  **detail strip** under the diagram (proposed; a floating box at the key is the alternative): the key as a cap row,
  then one line per assignment: its chord ("Alt+"), its full action text (`FormatControlAction` of the row) and its
  area. With no key hovered the strip shows the hint "Hover a key to see what it does".
- **Unbound and free keys.** A layout key with no assignment is drawn dim (the cap at `DIAGRAM_FREE_ALPHA` 0.45,
  proposed). A binding left without a key (a rebind can make one) shows in the strip's "Unbound" list.
- **Refresh (D13).** `SOLKeyDiagram::Build(rows, liveKeys, outModel)` runs when the page shows and on
  `OnKeyBindingsChanged`; the leaf paints from the cached model. Nothing is recomputed per frame; the only per-frame
  change is the hover ramp of at most two keys (the one gaining and the one losing hover).
- **Paint.** One leaf for the whole diagram: per key one hull box (the shared Small brush), one flat tint box, up to
  two texts; the mouse as boxes and lines. If the 33c profile shows the text cost over budget, the leaf goes under an
  `SInvalidationPanel` (it changes only on hover and rebind) (proposed fallback).

## 8. The HUD glossary (D5, D6, D7)

### 8.1 The symbol helper

`SOLHudSymbols::Build(ESOLHudSymbol symbol, FVector2f centre, float scale, FSOLHudSymbolPrims& out)` writes the
symbol's primitives into a fixed-capacity buffer (`MAX_PRIMS_PER_SYMBOL` 32, proposed): each a kind (line, ring, arc,
box, dot, dashed line, ellipse, sample text), its points and sizes in pixels at that scale, a palette role (Primary,
Secondary, Good, Hostile, FreeLook, Dim) and an intensity. Two replays:

- **HUD:** `ASOLFlightHud` replays the primitives through `GlowLine` / `GlowRing` / `GlowBox` / `GlowDashedLine` /
  `GlowEllipse` / `GlowDot`, so the shape renderer and the Canvas fallback both draw them as today. The draw methods
  keep what is not geometry (projection, on-screen tests, colour by state, the hint text).
- **Menus:** `SOLHudSymbols::AddToBatch(prims, batch, palette)` writes them into a `FSOLHudShapeBatch`.

Symbols with an existing builder are not re-implemented: the overlay icons and edge arrows call
`SOLOverlayIcons::AddIconShapes` / `AddEdgeArrow`, the cards `SOLHoloFrameBuild::BuildCard`, the radar plane and
stems `SOLRadar::ScopeToScreen` / `StemTop` / `ContactStyle`. **Geometry that is inline today moves into
`SOLHudSymbols` and the HUD calls it** (part 33d-i); the move is behaviour-neutral, proven by the existing HUD tests,
`-SOLSmokeHud` (reticle, Canvas fallback) and a before / after screenshot comparison.

`ESOLHudSymbol` (proposed): Reticle, Joystick, JoystickFreeLook, SteerFree, SteerHeld, SteerLocked, Prograde,
Retrograde, TargetBracket, TargetEdgeArrow, IconStar, IconPlanet, IconMoon, IconDwarf, IconAsteroid, IconRing,
IconShip, IconTarget, IconEdgeArrow, RadarScope, RadarContactAbove, RadarContactBelow, RadarSelected, GMeter,

### 8.2 Data table (D7)

`SOLMenuText::GLOSSARY_ENTRIES[]` (strings only, like `CONTROL_ROWS`):

```
struct FGlossaryEntry
{
    const TCHAR* Tab;         // One of GLOSSARY_TABS (the tab's full name)
    const TCHAR* Symbols;     // '|' list of SOLHudSymbols ids ("Prograde", "SteerFree|SteerHeld|SteerLocked"); "" = none
    const TCHAR* Sample;      // Glow text sample for a text element ("MANUAL|ASSISTED|AUTO"); "" = none
    const TCHAR* Name;        // Row heading
    const TCHAR* Description; // Body; '{<BindingId>}' = live key, '{<Token>}' = a constant (section 8.5)
};
```

`SOLGlossary` resolves each symbol id to `ESOLHudSymbol` (an unknown id is a test failure) and holds, in its `.cpp`,
the **coverage table**: for each entry the `ESOLHudLine`s, `EIconCategory`s, `ESOLHudCard`s, `ESOLSteerIcon`s and
`ESOLFlightMode`s it explains (the `UI/` enums stay out of `SOLMenuText.h`).

### 8.3 Drawing in the menu

Each glossary row's `USOLHudSymbolView` owns a small `SSOLHudShapeLayer` (`MaxShapes` `GLOSSARY_MAX_SHAPES` 128,
proposed) in **retain mode**, drawing with the solid menu subsystem's shared `M_SOLHudShape` MID (`EffectsStrength` =
the sanitized `HudEffectsStrength`, D14; `Composite` 1; view size = the layer's pixel size). The batch is built when
the view is first arranged and again only when its pixel size or the strength changes. Symbols are drawn at the HUD's
scale for a 1080-pixel canvas (`GLOSSARY_SYMBOL_UI_SCALE`, proposed), shrunk to fit the box when larger (the radar
scope, the radial menu, the cards). One custom-vertex draw per row (about 8-14 per tab). A dark backing like the HUD
panels sits behind each symbol so the additive glow reads as on the HUD.

## 9. The player guide (D8)

- **Flag:** `-SOLWritePlayerGuide` (`SOL::Smoke::WRITE_PLAYER_GUIDE` in `SOLConstants.h`; editor and development
  builds only, `!UE_BUILD_SHIPPING`), run with `-game -windowed -ResX=1920 -ResY=1080` by a new
  `Tools/WritePlayerGuide.bat` / `.ps1` (the `RunTests` pattern: refuses while the editor has the project open). It
  uses the smoke settings slot, so the keys are the defaults (D8), and the 46i settings snapshot, so the player's
  `GameUserSettings.ini` is untouched.
- **What it does:** starts in the main menu (like `-SOLMenuSmoke`), opens Help, and for each tab waits for the open
  and power-up to finish (strength 1), parks the cursor (no hover; one extra shot with a key hovered for the strip),
  and takes a window screenshot; then writes `SOLPlayerGuide::BuildMarkdown(DefaultKeys())` to
  `Docs/PLAYER_GUIDE.md` and moves the shots to `Docs/Images/33-help-keyboard.png`, `33-help-keyboard-hover.png`,
  `33-help-glossary-flight-hud.png`, `-targets-radar.png`, `-overlays-route.png`, `-menus-map.png`. Paths come from
  `SOL::Paths` (`PLAYER_GUIDE_FILE`, `PLAYER_GUIDE_IMAGE_DIR`, relative to `FPaths::ProjectDir()`). It logs
  `PlayerGuide WROTE ...` lines and quits; a missing page or a failed write logs `PlayerGuide FAIL` and exits non-zero.
- **Markdown (proposed, O9):** the banner, a "generated by `-SOLWritePlayerGuide`, do not edit" line with an input
  hash, an intro, then **Controls** (one table per area: keys as `<kbd>` tags, chords as `<kbd>Shift</kbd>+<kbd>M</kbd>`,
  the action text from `FormatControlAction`), the keyboard image, the area legend, then the **HUD glossary** (per tab
  the screenshot and a table of name and description). Nothing in it is hand-written.
- **Staleness (O12):** `SOLTest.PlayerGuide.UpToDate` loads `Docs/PLAYER_GUIDE.md` and compares it with
  `BuildMarkdown(DefaultKeys())`; a mismatch fails with "run Tools\WritePlayerGuide.bat". Whether this is a failing
  test or a warning step in `RunTests` is O12. The images are regenerated with the text; a change only to drawing code
  is not detected by the check (risk R5).
- **README:** a "Player guide" link in the README (33h) and the keyboard image in the gallery.

## 10. Pure logic contracts (test-first, for the separate test author)

Headless (no Slate, no RHI), in `Source/SOLTest/Tests/`; exact numbers from the constants, tables read through the
same headers. One file per topic:

- `KeyCapsTest.cpp` (`SOLTest.KeyCaps.*`): `ParseCell` of every `CONTROL_ROWS` cell at the default keys gives no
  empty alternative; `@` ids resolve (an unknown id is an unbound cap); chords split on `+`, alternatives on `|`;
  `Mouse2D` / `MouseWheelAxis` / `LeftMouseButton` give Mouse caps of the right button; Space, Backspace, Tab, Enter,
  Shift, Ctrl, Alt are Wide; an empty key gives one unbound cap; a chord binding (Shift+M) gives two caps; the cap text
  equals `FormatBindings`' text for the same cell (one source); `LayoutRow` wraps at the width, never splits a chord
  unless one chord is wider than the width, returns the height of its lines, handles zero / negative / NaN widths.
- `KeyboardLayoutTest.cpp` (`SOLTest.KeyboardLayout.*`): no two keys overlap; every key name is unique and known
  to the engine's key names used by the project; every default key of every binding (the chord's base key) and every
  fixed key of `CONTROL_ROWS` is on the layout or the mouse; `KeyAt` at each key's centre returns it, in gaps returns
  none, outside the extent none; scaling round-trips.
- `KeyDiagramTest.cpp` (`SOLTest.KeyDiagram.*`): at the default keys every binding is assigned to exactly one key
  (the binding has a cap, D15) and every key of a row is assigned; `O` holds four assignments with the four chords and
  primary OverlayMaster; `M` holds MatchLock (primary) and Shift+M OpenMap and the map's Move mode; a rebind moves the
  assignment and the old key becomes free; a binding on a key off the layout goes to the overflow list; an unbound
  binding goes to the unbound list; every area of `CONTROL_ROWS` maps to a palette colour (per O2); every short label
  exists and is at most `SHORT_LABEL_MAX_CHARS`; `Build` allocates nothing after a first build into the same model.
- `GlossaryTest.cpp` (`SOLTest.Glossary.*`): every `ESOLHudLine` (except `Count`), every `EIconCategory`, every
  `ESOLHudCard`, every `ESOLSteerIcon` and every `ESOLFlightMode` is covered by at least one entry (D6); every entry's
  tab is one of the four; names are unique; every symbol id resolves; `FormatEntryText` leaves no `{` at the default
  keys; no entry uses "²"; every binding id named in a description exists.
- `HudSymbolsTest.cpp` (`SOLTest.HudSymbols.*`): every symbol builds at least one primitive and at most
  `MAX_PRIMS_PER_SYMBOL`; its bounds scale linearly with the scale and contain every primitive; the reticle and the

  the constants say); the icon symbols add the same shapes as `SOLOverlayIcons::AddIconShapes` (one source);
  `AddToBatch` adds one shape per primitive (text samples excepted) and drops nothing in a batch of
  `GLOSSARY_MAX_SHAPES`.
- `PlayerGuideTest.cpp` (`SOLTest.PlayerGuide.*`): `BuildMarkdown` is deterministic, contains every `CONTROL_ROWS`
  action and every glossary entry name, every binding's default key in `<kbd>`, the banner and the generated-file line,

- **Existing tests to re-validate:** `SolidPageTabsTest` (Help tabs, `LeftColumnWidth(Help)`), `SOLMenuStateTest` (the

## 14. Performance and the VR floor

- **Budget (D12):** per screen under 0.2 ms extra CPU (game-thread Slate paint) and 0.3 ms extra GPU (Slate UI pass),
  three-run medians at 1920x1080 and 1280x720. Baselines: the Controls page **before** the cap restyle (captured in 33a
  with new `main-controls` / `pause-controls` passes in the default profile run); the Help pages against their menu's
  Settings baseline (the 46h rule for pages without a flat look of their own).
- **Profile passes (33f):** `-SOLSmokeSolidMenuProfile` gains `main-controls`, `pause-controls`, `main-help-keys`,
  `main-help-glossary` (the Flight HUD tab, the most symbols) and `pause-help-keys` in the default run and in the view
  runs.
- **Event-driven (D13):** no allocation in a paint or tick (the cap model, diagram model, prims and batches are
  reserved once); the diagram rebuilds on show and on a rebind only; a symbol view rebuilds on a size or strength
  change only; strength pushed into the shared MID only on change; nothing ticks while the page is hidden.
- **Draws (estimate, to be measured):** the diagram about 90 hull boxes, 90 tint boxes and up to 180 texts in one
  leaf; each glossary tab 8-14 custom-vertex draws plus its rows' text. The hull shader is the cost to watch on the
  caps (about 307 instructions a pixel, TECH_DEBT), and the diagram's text count on the CPU (fallback: an invalidation
  panel, section 7).
- **HUD regression:** the symbol move (33d-i) must not change the flight HUD's cost: `-SOLSmokeHoloMenuProfile` P0
  (flight, no menu) against its baseline and `-SOLSmokeHud` green.
- **VR floor (D15, review item 11):** view runs at 3840x2160 (the 4K proxy) and one XR-4 eye (3840x3744) with the
  menu-share verdict (`dcpu` <= 0.2 ms, `gpu_ui` <= 1.2 ms one eye); the two-eye (7680x3744) run per O8. The whole
  frame stays informational (scene-bound, project-level VR work, SDD 46 13.2).
- No cost claim without a measurement; the numbers go into an amendment of this SDD.
