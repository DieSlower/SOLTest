# SDD 8 — HUD, menus, controls/info/about screens, settings

Ticket `#8` (roadmap Part 7). Plan of record: [`Docs/Plans/8-hud-menus-settings-plan.md`](../Plans/8-hud-menus-settings-plan.md).
Refines SDD 1 and must not contradict it. Decisions were resolved with the user in a `grill-me` session on 2026-10-09.

## 1. Problem

The game has a flight HUD and a hint line but no menus: no way to start from a menu, pause, read what the controls and mechanics are,
change settings or quit cleanly, and CLAUDE.md's rule that an in-game info screen mirrors the mechanics has no screen to update.

## 2. Decisions

| # | Area | Decision |
|---|---|---|
| 1 | Menu set | A full main menu plus an Esc pause menu. |
| 2 | Main menu flow | Same map, a menu state over the live solar system: slow orbiting camera around a body, ship not yet spawned. Play spawns the ship (default start Earth orbit, honoring `-SOLStart`); a start-body picker offers any body. Entries: Play, Start location, Controls, Settings, About, Quit. |
| 3 | Pause menu | Esc opens tabs: Resume, Controls, Info, Settings, About, Quit to menu. Opening it does NOT pause the simulation (user choice): the sim and flight keep running, flight input is suspended while it is open (like the map's `SuspendShipControl`). |
| 4 | UI technology | UMG widgets created in C++ (no Blueprint widget assets), layout and formatting logic as pure functions with automation tests; matches the existing `SOLSpeedPanelWidget`. The flight HUD stays on `ASOLFlightHud` (canvas). |
| 5 | Settings content | Graphics (resolution, window mode, quality preset, vsync via `UGameUserSettings`), audio (master / SFX / music volume), controls (mouse sensitivity, invert Y, key rebinding via Enhanced Input user settings), gameplay (HUD scale/visibility, default flight assist). |
| 6 | Persistence | Per the project persistence standard: mutate in memory, one batched write at menu close, skip when unchanged, read once at boot, async where it is a `USaveGame`. A versioned schema for any custom save data. |
| 7 | Info screen | Generated from the real `SOLConstants.h` values (damage, shield, regen, speed caps, warp limits, ...) plus short static prose kept in one file, so it cannot go stale; `GAME_MECHANICS.md` stays the reference catalog. |
| 8 | Controls screen | Lists every binding, read from the live Enhanced Input mappings (so rebinding is reflected) with a static label per action. As built, rebinding is not Enhanced Input user settings but `SOLKeyBindings` overrides in the settings save, and the Controls page reads the ship pawn's mapped keys (or the applied settings in the main menu): see Amendment 2. |

## 3. Design

- Pure logic (test-first): `SOLMenuState` (menu state machine: MainMenu, Playing, Paused and legal transitions, input suspension rules),
  `SOLInfoText` (formats constants into display lines), `SOLSettingsModel` (clamping, dirty tracking, apply/revert, batch-save decision),
  `SOLBindingLabel` (key display names).
- Runtime: `USOLMenuSubsystem` (owns state and the widget stack), widgets `SOLMainMenuWidget`, `SOLPauseMenuWidget`, tab widgets,
  `USOLSettingsSubsystem` (wraps `UGameUserSettings` plus a `USOLSettingsSave`), game-mode changes so the ship spawn waits for Play,
  a menu camera pawn orbiting a body.
- Verification: automation tests for the pure logic, PIE smoke with screenshots of each screen, adversarial opus review.

## 4. Open questions

None deferred. The Esc key currently has no other binding to conflict with (verify when building).

## Amendment 1 — Parts 8b/8c as built (2026-10-09)

- **Ship lifetime.** The ship entity no longer exists at begin play when the main menu shows. `USOLShipSubsystem::SpawnPlayerShip(startBody)` is called by Play (start body from the picker, default `-SOLStart` or Earth) and `DespawnPlayerShip()` by Quit to menu (it also clears the surface-lock and the frame-carry history). Quit to menu also clears the selected target and any M frame lock. Dropped combat targets and live bolts are left in the world (they are world objects, not the ship's).
- **Pawns.** The game mode's default pawn class follows the menu state: `ASOLMenuCameraPawn` in the main menu, otherwise the ship pawn (or the `-SOLSpectator` camera). `USOLMenuSubsystem` swaps pawns itself (destroy the old pawn, spawn, `Possess`) instead of `RestartPlayer`, so no PlayerStart is needed. The menu camera is the observer: it sits 4.5 radii from the start body on its lit side, sways slowly, and moves to a newly picked body at once.
- **Esc.** `IA_ShipPause` (Esc) lives in the ship's mapping context only, so while the jump map is open its own Esc (in `IMC_Map`) closes the map and the pause cannot open. In the pause menu, Esc reaches the focused widget (UI-only input) and resumes. Requests are queued and applied on the next frame (outside Slate and Enhanced Input callbacks).
- **HUD.** The flight HUD is not drawn while the main menu or the pause menu shows.
- **Controls screen (decision 8 deviation).** The Controls page is a static table (`SOLMenuText::CONTROL_ROWS`, engine key names shown through `SOLBindingLabel`), not read from the live mappings: the ship's mapping context is created by the pawn, which does not exist in the main menu. Part 8d replaces it with the live mappings when rebinding lands. `SOLBindingLabel` gained four display names (Hyphen, BackSpace, MouseWheelAxis, Mouse2D); its API is unchanged.
- **Command line.** The menu is skipped when any other `-SOL*` switch is present (all smoke, demo and start flags), so verification runs start in flight exactly as before. New: `-SOLMenu` (force the menu), `-SOLNoMenu` (skip it), `-SOLMenuSmoke=<all|screens|flow>` (scripted walk with screenshots; `screens` is the same as `all`, `flow` takes none).
- **Settings tab** is a heading-only placeholder until 8d.

## Amendment 2 — Part 8d as built (2026-10-09)

- **Settings subsystem.** `USOLSettingsSubsystem` is a game-instance subsystem holding the 8a `SOLSettingsModel::FSettingsModel` (API unchanged), the applied and pending key arrays, and the pending resolution and window mode. The model has no fields for resolution and window mode, so those stay with `UGameUserSettings` (which applies them when the window is created) and the subsystem keeps only their pending values.
- **Persistence (decision 6).** `USOLSettingsSave` (a `USaveGame`, slot `SOLSettings`, `Version` = `SOL::Settings::SAVE_VERSION` = 1) is read once at boot. `SOLSettingsRules::ClassifySaveVersion` uses a same-version save, migrates an older one (`MigrateSave`, empty until a schema 2 exists; the upgraded file is written at the next write point) and ignores a missing, unversioned or newer one without touching it. Apply only changes memory (`CommitIfDirty` marks a write as owed); the write happens in `EndVisit`, when the Settings page is left or a menu opens or closes: one `AsyncSaveGameToSlot` if owed, plus one `UGameUserSettings::SaveSettings` if the engine settings changed (`ApplySettings` was not used, because it saves on every call). Shutdown (`Deinitialize`) writes synchronously, since an async write could be cut off. Unapplied changes are discarded when the page or menu closes. Without a save, vsync and the quality preset start from the engine's values, so a first run writes nothing.
- **Apply vs preview.** Audio volumes, mouse sensitivity / invert Y and HUD scale / visibility preview from the pending values at once and are reverted by Revert or leaving the page; vsync, quality, resolution, window mode and key bindings take effect on Apply; the default flight assist is read at the next ship spawn (both `USOLShipSubsystem::SpawnPlayerShip` and the pawn's start state). An Apply pushes vsync and quality to the engine only when the player changed them, so an engine "custom" scalability mix (level -1) survives unrelated Applies. Inside the editor, resolution and window mode are stored but not applied (the PIE viewport is not the game window).
- **Audio.** No sound classes existed. `Tools/CreateSOLAudioClasses.py` created `/Game/SOL/Audio/SC_SOLMaster` with `SC_SOLSfx` and `SC_SOLMusic` as children and assigned `SC_SOLSfx` to the seven combat `S_SOL*` waves. The volumes are class overrides on one runtime `USoundMix` pushed on the game world at begin play (master applies to its children; the adjusters multiply: verified on the audio thread as 0.5 x 0.8 = 0.4). Music has no content yet; its class and slider exist.
- **Key rebinding (decision 5 deviation).** Not Enhanced Input user settings: the ship's mapping contexts are transient objects the pawn builds in C++ (no assets, and a new pawn per Play), which the user-settings route expects as registered assets with player-mappable key settings, and it would add a second save file outside the persistence standard. Instead `SOLKeyBindings` defines the 29 rebindable ship actions (stable ids, labels, default keys = the old hardcoded ones), overrides (id -> key name, only those that differ) are stored in `USOLSettingsSave::KeyOverrides`, and the pawn builds its mappings from the applied keys (`MapShipKeys`) and maps them again on `OnKeyBindingsChanged` with a control-mapping rebuild. Fixed and refused: Esc (pause), the mouse look axes, the wheel and P (reserved). The jump map's own keys (left / right / middle mouse, Left / Right Shift, X, Enter) stay fixed in the map's context; the ship actions may still use them (the two contexts are never active together), but the map toggle J, which is rebindable and mapped in both contexts, refuses them (corrected in Amendment 3: as first built nothing stopped the toggle from taking one). A key already used by another action is accepted with a warning and both rows are flagged (no silent swap). Gamepad keys are not handled specially.
- **Controls screen (decision 8, closes the Amendment 1 deviation).** `SOLMenuText::CONTROL_ROWS` cells for rebindable actions are `@<id>` tokens; the Controls page rewrites its key cells whenever it is shown from `SOLMenuContent::ResolveLiveKeys`: the ship pawn's actually mapped keys in flight, the applied settings keys in the main menu (no pawn there). The flight HUD's key hint line was hardcoded too ("LMB fire", ...) and now comes from `SOLHudFormat::FormatFlightKeyHints` (cached, rebuilt only on a rebind), so it stays truthful.
- **Settings page UI.** `USOLSettingsPageWidget` (C++ UMG, shared by both menus): steppers for resolution / window mode / quality, checkboxes for vsync, invert Y, HUD visible and flight assist at launch, sliders for the three volumes, mouse sensitivity and HUD scale (stock UMG slider and checkbox styles, tinted), one row per key binding with Rebind, Reset keys, Revert, Apply, a dirty indicator and a status line. Rebind captures the next key or mouse button in the preview phase so neither the focused button nor the menu's own Esc handling sees it.
- **HUD.** The HUD scale multiplies the existing canvas-height scale; with the HUD hidden nothing of the flight HUD draws in flight, but the jump map still draws its overlays and the warp streaks still play.
- **Directional-light warning.** The editor's on-screen "multiple directional lights are competing" message came from the Sun light and the ship's fill light sharing forward-shading priority 0. The Sun light now has `ForwardShadingPriority` = `SOL::SUN_FORWARD_SHADING_PRIORITY` (1), so it is always the forward-shading / translucency light; the fill light is unchanged. The message no longer appears in the smoke screenshots.
- **Verification.** `-SOLMenuSmoke=all` drives the page through its own setters on a separate slot (`SOLSettings_MenuSmoke`, deleted at start): two Applies then leaving the page give exactly one write, an unchanged visit gives none (file time unchanged), re-reading the slot restores the values, preview + Revert, the mixed effects volume, HUD scale in flight, a refused / conflicting / real rebind (Fire to K; the pawn's mapping has K and not the left mouse, the Controls tab and HUD hints show K, holding the left mouse fires nothing, holding K fires bolts), the rebind written once on resume, and the starting settings restored at the end. 40/40 checks passed. Caveat: the smoke's own slot keeps the player's file untouched, but its quality changes go through the engine's `GameUserSettings.ini`; when the engine started on a custom scalability mix the restore leaves it on the Epic preset.
- **Not done / open.** Resolution and window-mode changes were not exercised by the smoke (they would resize the test window); no confirm-or-revert timer after a resolution change; the Settings controls use the stock slider and checkbox looks.

## Amendment 3 — 8e adversarial review fixes (2026-10-12)

- **Rebind capture.** The page's preview-phase key handlers only saw keys while the keyboard focus was inside the page, and a hovered menu button takes focus, so Space while hovering Resume or Quit clicked it. The capture is now a Slate input pre-processor (`IInputProcessor`) the Settings page registers while it is constructed: while listening it takes the next key or mouse press before any widget (whatever has focus) and swallows its release; menu buttons skip hover-to-focus while a capture is active (`USOLSettingsSubsystem::IsKeyCaptureActive`). The smoke drives it through real Slate events with the focus forced onto the Resume tab.
- **Boot graphics.** Without a save the model shows Epic over an engine custom mix (-1); any later save stored that 3 and the next boot pushed it, overwriting the custom mix. The save now records whether the player chose vsync / the quality preset on the page (`bVsyncChosen`, `bQualityChosen`, added within schema 1: older files read false). At boot `SOLSettingsRules::DecideBootGraphics` (pure, tested) pushes only a chosen value that differs from the engine's; everything else starts from the engine.
- **Map toggle keys.** `SOLKeyBindings::CanBindKeyTo` refuses the jump map's fixed keys for `ToggleMap` (Rebind and save overrides); Amendment 2's wording is corrected above.
- **Texts that name keys.** The surface-lock hint, the `[M LOCK]` tag, the target panel's `none (T)`, the speed panel title (and its closing key), the Info page's manual surface-lock label and prose are `{<BindingId>}` formats in `SOLMenuText` filled by `SOLKeyBindings::FormatKeyText`; the HUD caches them with its hint lines (rebuilt on `OnKeyBindingsChanged`), the Info tab rewrites them when shown, the speed panel when opened. The Controls table's "200 m" and "10 notches" come from `COMBAT_TARGET_DROP_DISTANCE_M` and `SOLFlight::SpeedCapStepsPerDecade`.
- **Saving.** Async writes are counted in flight until they report back; a failed one makes the write owed again; `Deinitialize` writes synchronously if a write is owed or still in flight (an unfinished async write holds the same content).
- **Corrupt keys.** `ResolveKeys` drops key names the engine does not know and axes (`IsPressableKey`), so a bad save falls back to the defaults.
- **Smaller fixes.** A held Esc's auto-repeat no longer resumes from the pause menu; the ship pawn keeps the spawn's flight-assist state (a `-SOLRingStartKm` start stays assist-off); the volume mix is popped when its world is torn down; Quit to menu cancels a running jump warp (`USOLJumpSubsystem::CancelJump`); the unused `OnSettingsChanged` delegate is gone; `ShouldStartInMenu` compares the `SOL` prefix case-insensitively like the switch names; the model's clamps use the `SOL::Settings` ranges; the key-binding labels, Info combat labels and HUD hint formats moved to `SOLMenuText`; the menu button padding moved to `SOL::MenuStyle`. The Info prose no longer says the Sun is the only light (the ship has a fill light).
